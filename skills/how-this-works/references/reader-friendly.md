# 面向新读者的项目解释

语言是学习产品的一部分。读者不应为了理解你的结论，先自行补齐你研究时已经掌握的背景。

当前以理解图、项目解释与按需读取的单元组织内容。认识用途后，先说明整体思路，再深入实际发现的关键设计选择。功能、环节、职责和机制不必构成固定层级；每个单元说明它与整体或原问题的关系。理解图保留上层及直接相关单元的上下文，解释就近展开；基础材料使用清单与原文核验。

“做什么”和“为什么这样做”要相邻。围绕一个选择，把具体困难、选用办法、代价和适用条件解释完整；不要把目的与方法拆到不同层级，要求读者下一次点击才能接上推理。标题和段落随材料组织，不强制每项都有相同数量的小节。历史中的偶然、兼容需要、失败与未知理由也要保留，不能把现在的每一行实现合理化为作者深思熟虑的决定。

## 写作的落点

首先检查读者是否已经知道这个项目干什么。没有这层共同认识时，先解释使用者、场景、功能与一次使用的输入输出，再介绍内部机制。不能拿“为什么索引会出错”作为连“为什么需要索引”都不知道的读者的第一课。

研究者需要读代码，不意味着学习者应先读代码。用一个完整使用过程交代用户、助手和工具各自的工作；示意流程与实测结果明确区分。介绍页可以保持证据折叠，读者应能只读正文就建立项目定位。功能名称要说明能帮助完成什么任务，不用内部架构特点充当用户功能。

摘要帮助选择入口；进入职责或问题以后，用连贯段落展开。具体篇幅由推理需要决定，不规定字数或必填小节。读者需要的通常是：发生了什么，为什么原方案处理不了，改变了哪个责任或条件，以及新选择还留下什么代价。

术语在需要时引入，并解释它在当前场景中的作用。函数名和证据链接用于定位，不承担正文尚未完成的解释。需要读者从 A 推到 C 时，补出 B；避免把内部操作连续堆成一句话。

例如，“增量索引要维护来边”不足以解释问题。先说明 A 调用 B、只改 B 时旧节点被删除，数据库的级联规则会同时删掉 A 指向 B 的边，而 A 又未被重新提取。读者由此才能理解，为何“更新变化文件”不等于“关系仍然正确”，也知道应到源码中核对哪一步。

## 当前与历史

当前正文解释职责、契约、关键条件与边界。演化正文讲清旧方案在当时解决什么、后来暴露什么限制、为什么发生收缩或替换；不能用今天的结果把过去写成显然错误。

没有作者理由时，可从实现解释成本和约束，但要明确这是推断。提交正文中的理由也是可用材料，不能只读标题就声称动机未知。存在后续纠正时，保留它如何改变前一次判断。

删除不表示问题消失，重新出现不证明连续继承。保留历史职责的退出状态、旧版本证据及可能的接替关系，分别说明“实现消失”“问题延续”“效果是否等价”。

## 在结论附近保留边界

作者报告、当前源码、测试断言和实际运行是不同材料。读者不应读到文末才发现重要结论只是推断。性能比例需附适用条件；沿用前轮实验时明确时间，不冒充本轮重跑。

较充分的解释也不能靠重复免责声明来充数。边界应帮助读者判断：这条认识适用在哪里，条件变化后要验证什么。

## 写作时自检

撰写当前单元时检查以下问题，不另增加抽查或独立复核步骤：

- 完全没读过源码的人，能否先说清项目干什么、谁用、何时用和返回什么？
- 是否能在没有研究者背景的情况下理解场景与术语？
- 能否用自己的话连起主要协作，解释项目把哪些工作提前准备、按需执行或交给外部承担？这些是观察问题，不预设项目必须有预计算。
- 是否知道原方案为什么看似合理，又在哪里不够？
- 能否找到支撑关键转折的实际代码或作者材料？
- 是否分清实现事实、取舍推断与尚未独立验证的效果？
- 改变什么条件，会使替代方案重新值得考虑？

记录发现的具体跳步与改写前后例子。研究 Agent 的自检只证明已经做过阅读审查，不能声称真实用户已掌握；浏览器测试只验证呈现与交互。

## 摘要与证据复核

先独立阅读摘要，再对照详细解释和支撑材料，检查摘要是否把“某阶段只读”压缩成“所有准备操作只读”，或把“某入口有门槛”推广到全部入口。影响结论的例外放回摘要。

每条证据记录它具体支持的判断。位于源码中的purpose、help、description字符串仍表达声明，不能单凭文件后缀作为限制已执行的证明。对实际行为的解释应读到检查分支、消费者及必要的失败处理；未取得这些证据时缩小陈述或保留缺口。

正文先用读者能理解的场景讲清接手什么、关键选择和结果，再引入项目术语。不要把术语表、函数名序列或反复声明“未运行”当作连贯解释。

节点标题先用读者能理解的职责描述，例如“决定下一步是否执行”；对应的英文术语和代码名在正文首次使用时解释。不要让标题只罗列内部名词。

学习入口先用具体情境讲清项目用途，再跟随一件事理解过程，回看职责分工并深入关键选择。场景解释“各部分在这件事里怎样配合”，单元解释自身职责和机制；不重复整篇正文。条件与例外就近说明，并保留支撑判断的原文入口。

首页用项目用途、例子和场景选择作为起点，不默认展示陌生职责图。整体架构用于学后回看：保留来时场景和步骤，把具体步骤归纳到实际参与职责，并帮助发现同一职责在其他场景中的作用。不要再设置与“认识项目”同义但无独立用途的“项目全貌”入口。

从场景进入职责时，先给白话的职责说明，再引入实现术语；关系说明也使用读者的主要语言。场景如果承诺操作，应给出材料支持的具体入口和结果核对方式；静态分工示例与完整操作教程的边界要清楚，不把未验证的接入或恢复路径补写成事实。
